# Choose the learning outcome

| Outcome | Use when | Proposed result |
| --- | --- | --- |
| Case | A concrete episode, correction, blocker or result needs a traceable record | Concise case plus separate evidence; causes may be unknown |
| Knowledge note | A useful explanation, discovery, decision rationale or tradeoff is reusable without prescribing behavior | Neutral scoped learning note; no automatic Good practice label |
| Rule candidate | A short supported constraint, stable preference or invariant should influence future behavior | Prefer a targeted change to an appropriate existing rule; state project/directory/global scope |
| Skill candidate | A reusable multistep workflow has clear triggers, inputs, outputs and acceptance | Prefer updating a matching skill; otherwise propose a narrowly named new skill |

Search the relevant existing assets before recommending creation. Explain whether the lesson is new, an edge case of an existing asset, conflicting with one, or only a local case. Preserve the user's existing writing/filing conventions. A single event may justify a case without a universal rule; repetition alone does not prove a root cause or justify a new skill.

A skill recommendation describes when it should run, what it should do, required tools/context, boundaries and how to verify its output. A concrete application proposal stages its actual files and diff. Do not create or install it in a discoverable skill location until that action is explicitly approved. Use the skill-creation workflow available in the execution environment when appropriate, without assuming another harness has Codex-specific tools.

For rule or skill changes inspect the real host conventions and current files. Do not hardcode Antigravity paths or RPC/UI mechanisms for another harness. Shared configuration changes retain the applicable fresh-read, backup, concurrency and validation procedure. If the approved baseline changed, reconcile before applying rather than overwriting it.

The workflow draws on Google's [learn command documentation](https://antigravity.google/docs/commands/learn): distill, classify, prefer an existing asset, propose, and apply only within real human approval. This implementation also supports neutral knowledge and unresolved cases. Owner-specific assignments and historical exceptions are local configuration.
